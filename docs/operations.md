# Operating MOD Core CE

Running, securing and upgrading an install: secrets, first login and adding people, access from other computers, the node builder, GPUs, OpenBao and the Keycloak realm. [Back to the README](../README.md).

## Running Community Edition

`docker-compose.yml` (this repo root) is a single-host compose file for the
Community Edition. It ships no external env files, no payment system, and no
private registry — but it is **not** secrets-free: every infra credential
(`POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `VERSITYGW_ROOT_ACCESS_KEY`/
`_SECRET_KEY`, `KEYCLOAK_DB_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`,
`KEYCLOAK_REALM_ADMIN_PASSWORD`, `SECRET_ENCRYPTION_KEY`, `PLATFORM_SERVICE_API_KEY`, `AUDIT_HMAC_KEY`) is required
(`${VAR:?...}`, no default) and must come from `scripts/first-run-secrets.sh`
(see Quickstart above) — `docker compose up` fails fast with a `run
scripts/first-run-secrets.sh` error if you skip it. Likewise the Keycloak
client secrets (`KEYCLOAK_FASTAPI_CLIENT_SECRET`,
`KEYCLOAK_FASTAPI_ADMIN_SECRET`, `KEYCLOAK_DASHBOARD_CLIENT_SECRET`,
`KEYCLOAK_SERVICE_CLIENT_SECRET`) have no fixed default; they are generated by
the installer, and you do not set them. If you skipped the installer, run
`./keycloak/ensure-client-secrets.sh` once (before `docker compose up`) to
generate random values for any of them that aren't already set, written into
the same `.env` file.

> ## First run
>
> `scripts/first-run-secrets.sh` generates every required infra credential as
> a random value into `.env` (mode 0600). It never rotates secrets out from
> under a running stack. It appends any missing keys on re-run (e.g. ones
> added by an upgrade) and never overwrites existing values — so it's safe
> to re-run after an upgrade. There is no "obvious placeholder" default
> anymore: a fresh checkout with no `.env` simply won't start.

### Start it

Run `./scripts/install.sh` from the [Quickstart](./install-guide.md#quickstart) above (it runs the same
steps; they are not repeated here). Then:

If you already started the stack before running
`./keycloak/ensure-client-secrets.sh`, the imported realm carries placeholder
client secrets — see "Resetting Keycloak (re-runs only)" above. **That step
DELETES ALL KEYCLOAK USERS**; skip it on a first bring-up.

All ports bind to `127.0.0.1` by default (the two opt-in compose profiles are the
exception: with the `registry` profile on, the image registry listens on
`0.0.0.0:5000` — every interface, so other worker machines can pull built nodes;
set `REGISTRY_BIND=127.0.0.1` to keep it on this machine. With the `stack-ingress`
profile on, the edge listens on `8880`/`8443` at the same address as the browser
ports). Once up:

- **API**            — http://localhost:8000  (OpenAPI at `/docs` when the `api.public_docs_enabled` platform setting is on (default ON in CE, so anonymous callers get the docs; set the setting to off if you do not want public API docs))
- **Dashboard**      — http://localhost:3000
- **WorkflowBuilder** — http://localhost:3001
- **Keycloak**       — http://localhost:8080  (admin console under the creds below)
- **Postgres**       — 127.0.0.1:5432 · **Valkey** — 127.0.0.1:6379 · **versitygw** — 127.0.0.1:7070
- **OpenBao**        — 127.0.0.1:8200  (tenant-secrets store; API at `/v1/*`)
- **Mailpit**        — http://localhost:8025  (local SMTP relay: the web inbox
  shows every email CE sent; SMTP itself is 1025 on `modtex-network` only)
- **File downloads, previews and 3D** — `http://localhost:7070` (S3); presigned
  URLs point at that host, so it must stay reachable from the browser.

### Rotating secrets

The first-run script never rotates a value: it only fills keys that are
missing, and editing `.env` by hand and re-running it does not change an
existing key. Community Edition has no supported online rotation for the
infra keys below, so to change one of them, back up your data first, then
wipe and reinstall the stack.

| Key | What it covers | Supported path |
|---|---|---|
| `POSTGRES_PASSWORD` | Database login used by the platform services | no supported online rotation: back up, reinstall |
| `REDIS_PASSWORD` | Valkey (Redis) login | no supported online rotation: back up, reinstall |
| `KEYCLOAK_DB_PASSWORD` | Keycloak's database login | no supported online rotation: back up, reinstall |
| `KEYCLOAK_ADMIN_PASSWORD` | Keycloak admin console login | no supported online rotation: back up, reinstall |
| `KEYCLOAK_REALM_ADMIN_PASSWORD` | Keycloak realm admin login | no supported online rotation: back up, reinstall |
| `SECRET_ENCRYPTION_KEY` | Fernet key for values the platform encrypts at rest | no supported online rotation: back up, reinstall. Setting a new key without the old one makes data already encrypted with it unreadable. |
| `AUDIT_HMAC_KEY` | HMAC key for the audit-log hash chain; a new key does not verify existing signatures | no supported online rotation: back up, reinstall |
| `PLATFORM_SERVICE_API_KEY` | API key of the platform service account | no supported online rotation: back up, reinstall |
| `VERSITYGW_ROOT_ACCESS_KEY` | Storage root access key (admin calls) | no supported online rotation: back up, reinstall |
| `VERSITYGW_ROOT_SECRET_KEY` | Storage root secret key (paired with the access key) | no supported online rotation: back up, reinstall |
| `MOD_INGRESS_ASK_TOKEN` | Shared token for the stack-ingress edge | no supported online rotation: back up, reinstall |

The four Keycloak client values `KEYCLOAK_FASTAPI_CLIENT_SECRET`, `KEYCLOAK_FASTAPI_ADMIN_SECRET`, `KEYCLOAK_DASHBOARD_CLIENT_SECRET` and `KEYCLOAK_SERVICE_CLIENT_SECRET` are generated the same way by `keycloak/ensure-client-secrets.sh`, which also never overwrites a value that is already set; they have no online rotation path either.

Never blank a value in `.env` by hand: an empty key counts as absent, so
the next run of the script writes a new random value in its place.

### First login and adding people

1. Log in to the Dashboard at http://localhost:3000 as `admin@core.local`
   with `KEYCLOAK_REALM_ADMIN_PASSWORD` — see
   [Community Edition — Keycloak realm & dev credentials](#community-edition--keycloak-realm--dev-credentials)
   below for where that password lives.
2. Self-registration is OFF on Community Edition (`registrationAllowed: false`
   in `keycloak/core-realm.json`): there is no Sign-up link, by design.
3. To add a person, open the Dashboard Invitations page: "Send Invitation"
   invites someone into your tenant (the invitations API). CE has
   no outbound email provider, so by default copy the accept link the page shows
   you (`http://localhost:3000/accept-invitation.html?token=…`) and send it to
   them yourself (e.g. teammate@example.com).
   To see the email path end to end on your own box, use the shipped local SMTP
   relay: Dashboard Settings -> Integrations -> Email (SMTP) -> the "local" preset (host `mailpit`,
   port 1025, encryption none), then read the invitation at
   http://localhost:8025 — Mailpit's web inbox shows every email CE sent.
4. They open the link and set their own password — the accept page enforces at
   least 12 characters (the realm's `length(12)` policy from
   `keycloak/core-realm.json`, mirrored client-side in
   `CORE/Dashboard/js/accept-invitation.js`); passwords the API itself sets go through
   the stricter API password-policy gate (`password_policy.py`), whose `MIN_LENGTH` is
   15. The invite expires after the period set in the invitation policy
   (platform setting `external_collab.default_expiry_days`, default 90 days).
5. The accept pages have no separate rate limiter in CE: the API's app-level guard
   (`CORE/API/services/api_rate_limit_guard.py`, platform settings `api.rate_limit.*`) is
   unlimited by default in Community Edition (an operator can still set limits); a client IP that fails authentication repeatedly
   is auto-blocked, and `/public/` paths are exempt from throttling (not from the auto-block).
6. To re-enable self-registration (not recommended), use the Keycloak admin
   console → realm `modtex` → Realm settings → Login → "User registration".

### Accessing CE from another machine

By default MOD listens on this computer only (`127.0.0.1`). To reach it from a
laptop or another machine, open it to your network with one command; no
variables to edit:

```bash
./scripts/install.sh --lan                  # open to the network, address auto-detected
./scripts/install.sh --host mod.office.lan  # open to the network, use this name or IP
./scripts/install.sh --no-lan               # back to this computer only
```

The old address stays in the Keycloak client list; it cannot be reached while the ports are closed.

Then browse to `http://<that address>:3000` from the other computer. The
installer sets every address variable from that one host (`PUBLIC_HOST`,
`BASE_DOMAIN`, `KC_HOSTNAME`, `KEYCLOAK_HOSTNAME`, `KEYCLOAK_EXTERNAL_URL`,
`DASHBOARD_URL`, `MOD_DASHBOARD_URL`, `MOD_API_URL`, `MINIO_PUBLIC_ENDPOINT`
and the browser-facing bind address) in one marked block of `.env`, and the
Keycloak setup container adds the host to the three realm clients on every
start. Passwords and data are never touched.

**Opening it to your network.** Anyone on that network can reach the sign-in
pages (Dashboard 3000, Workflow Builder 3001, Docs 3002, API 8000, Keycloak
8080 (or `KEYCLOAK_HOST_PORT`), file storage 7070, which answers any browser origin by default through `VGW_CORS_ALLOW_ORIGIN`; this is unchanged). Traffic is plain HTTP, so use it on a network you
trust (home, office LAN), not the open internet or public Wi-Fi. The
databases, Valkey, OpenBao and the mail catcher are never opened.
CE trusts only loopback for forwarded headers (X-Forwarded-For / X-Real-IP):
a LAN client that reaches the API directly is identified by its own peer
address, and on Docker Desktop/WSL every LAN client shares one bridge
gateway address, so they share one rate-limit/lockout key; if you put your
own reverse proxy in front of the API, set the proxy's address in BOTH
Platform Settings (`net.trusted_proxy_cidrs`) and the api service's
`FORWARDED_ALLOW_IPS` env line, or real client IPs stay lost.

**If the address changes** (a new DHCP lease), run `./scripts/install.sh --lan`
again: it updates only the address, keeps your passwords and data, and
restarts only what changed. Plain `docker compose up -d` never opens the
network by itself; it keeps whatever the installer last wrote.

**Check at any time** with `./scripts/ce-doctor.sh` (the `lan-hosts` and
`bind-addrs` lines).

Settings you can set in `.env` (all optional; the defaults are right for one
computer):

| Variable | Default | Meaning |
|---|---|---|
| `PUBLIC_HOST` | `localhost` | the name or IP other computers use |
| `CE_BIND_ADDR` | `127.0.0.1` | address the browser-facing ports listen on (`0.0.0.0` in network mode) |
| `KEYCLOAK_HOST_PORT` | `8080` | host port for Keycloak; `scripts/install.sh --keycloak-port N` changes it (use it when 8080 is already taken) |
| `CE_REQUIRE_ISOLATED_BUILD` | `1` | node builder: a build that cannot reach the isolated BuildKit sidecar fails with `BUILDER_UNAVAILABLE` after 20 s and never falls back to the host Docker daemon. Leave at `1`: setting `0` lets builds run on the host Docker daemon (root on the host) and weakens build isolation |
| `CE_BUILDKIT_FW_MODE` | `enforce` | egress policy of the BuildKit sidecar: `enforce` allows the public internet and blocks LAN and private ranges; `off` removes the policy so builds can reach the LAN. Leave at `enforce` |
| `CE_BUILDKIT_FW_ALLOW` | empty | extra CIDRs builds may reach besides the public internet, for example a local registry as `<ip>/32` |
| `CE_BUILDKIT_CONFIG` | `./CORE/DockerContainers/buildkitd/buildkitd.toml` | optional BuildKit daemon config, mounted read-only into the sidecar (for example a local `registry:2` over HTTP) |
| `CE_BUILDKIT_HOST` | `tcp://buildkitd:1234` | address the platform uses to reach the BuildKit daemon |
| `CE_BUILDKIT_CPUS` | `2` | CPU limit of the BuildKit sidecar |
| `CE_BUILDKIT_PIDS` | `2048` | process limit of the BuildKit sidecar |
| `STACK_TLS_ISSUER` | empty | certificate source of the stack-ingress edge: `letsencrypt` or `vault-acme` (OpenBao PKI ACME). Unset, the edge serves only its health endpoint and issues nothing. Needs the `stack-ingress` profile |
| `STACK_TLS_ACME_EMAIL` | empty | optional ACME account email for `letsencrypt` and `vault-acme`; blank means no email is sent |
| `STACK_INGRESS_APPS_WILDCARD` | `*.apps.<BASE_DOMAIN>` | host pattern of app stacks served over HTTPS by the stack-ingress edge |
| `STACK_INGRESS_SERVICES_WILDCARD` | `*.services.<BASE_DOMAIN>` | host pattern of service stacks served over HTTPS by the stack-ingress edge |
| `STACK_INGRESS_HTTP_PORT` | `8880` | host port the stack-ingress edge publishes for HTTP |
| `STACK_INGRESS_HTTPS_PORT` | `8443` | host port the stack-ingress edge publishes for HTTPS |
| `DOCS_SUBDOMAIN` | empty | subdomain label of the docs site under `BASE_DOMAIN` |
| `DOCKER_NETWORK` | `mod_modtex-network` | Docker network that worker-launched containers join |
| `PROTOCOL` | `http` | URL scheme the platform uses in generated links (`http` or `https`) |

If you reach CE without opening the network, an SSH tunnel also works:

```bash
ssh -N -L 3000:localhost:3000 -L 3001:localhost:3001 -L 8000:localhost:8000 \
  -L 8080:localhost:8080 -L 7070:localhost:7070 <user>@<ce-host>
```

When you bind a LAN address, install the reboot drop-ins: DHCP can assign the
address after dockerd has restored containers, and those containers then fail
to start with `cannot assign requested address`; see
`scripts/mod-ce-recover.service` and the `docker.service.d` drop-in described
in that template.

### How workers reach your install

Workers connect to your Community Edition install over your own network (LAN). Optional mesh anchors (site and cloud) are not part of Community Edition, so a worker never needs, and never tries to reach, a headscale or tailnet control server.

### Node builder: the BuildKit AppArmor profile

The node builder runs a rootless BuildKit sidecar (`buildkitd`, `builder` profile).
On an AppArmor host (Ubuntu 23.10+, 24.04, 26.04) its profile must be loaded once per
host before the builder starts. Run this from the extract root, as root:

```
sudo ./scripts/install-buildkit-apparmor.sh
docker compose --profile builder up -d
```

The script copies the profile to `/etc/apparmor.d/mod-buildkitd`, loads it and
keeps it across reboots; running it again is harmless. The installer runs this
step itself when it can do so without a password prompt (as root, or with
passwordless sudo). Otherwise it prints the command above to run later and
continues without the node builder. If the script prints `CE_BUILDKIT_APPARMOR=unconfined` (no
AppArmor, or a kernel that does not gate user namespaces), put that line in `.env`
instead and skip the install.

Ubuntu 24.04 and newer: the node builder runs build steps in an unprivileged user
namespace, and AppArmor restricts these by default. If builds fail with an `unshare`
permission error, allow them: `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`
(applies until reboot). To keep it across reboots, add the line
`kernel.apparmor_restrict_unprivileged_userns=0` to a file in `/etc/sysctl.d/`.
Older Ubuntu releases and most other distributions need no change.

### GPU

CE v1 runs node containers on CPU by default: the compose file does not configure GPU
passthrough to them. GPU workers are a preview: a separate GPU worker machine can
join, but GPU jobs are not yet proven end to end in v1.0.0. The `mod-worker` service only passes `HOST_GPU_TYPE`
(default `none`), `HOST_VRAM_GB` and `HOST_GPU_NAME` through as hardware labels,
and declares no GPU device reservations. GPU-bound nodes run on a separate GPU
worker you add (see the [worker setup page](../CORE/docs-site/docs/worker-setup.md)).

`docker compose down` stops it and keeps your data. Adding `-v` deletes every named data volume, including the database and the OpenBao unseal key; the stored-files ciphertext directories and the host key file are not removed by `-v`; they survive it and must be removed separately, both together or neither (see the uninstall page). Back up first, and see [Stop, remove or fully uninstall a Community Edition install](../CORE/docs-site/docs/runbooks/uninstall-ce.md).

OpenBao (tenant-secrets KV/AppRole/database/transit store) ships bundled and
self-initializes on first `docker compose up` via the `openbao-init` one-shot
service (`scripts/first-run-openbao-init.sh`) — its local unseal key is
written to the `openbao-init-state` volume at mode 0600; never commit or copy
it off the host for anything beyond a local trial.

### OpenBao audit device

Every OpenBao request (break-glass policy edits, secret reads) is logged by a
declarative `audit` stanza in the server config to the `openbao-audit` volume
at `/openbao/logs/audit.log` (mode 0600, HMAC'd secret values — never raw).
The log grows: archive it, never delete it (ISO 27001 A.8.15). If OpenBao
cannot write the log it refuses requests it cannot log — the volume must stay
writable; a fresh init shows exactly one device (`bao audit list` → `file/`).
If the volume is not writable at start, OpenBao comes up SEALED (every request
503) and the log shows `failed to create new audit device file/`; fix the
volume's permissions and restart — never delete the log to "clear" it.

### Upgrading OpenBao policies

A fresh CE init mints a break-glass AppRole whose policy (`policy-admin`) can WRITE only
these paths: ACL policies (`sys/policies/acl/*` create/update/read, `sys/policies/acl`
list — no delete), the app DB engine config and role (`database/config/app-db` and
`database/roles/api-readwrite`: create/update), and two single bootstrap-token slots,
`secret/data/infrastructure/embedded-worker` (the built-in worker's token) and
`secret/data/infrastructure/ingress` (the edge ask token): on each exact path it has
create + read only, so it may CREATE a slot when it is missing and never update or delete
it. It also reads its own policy paths and revokes its own login token
(`auth/token/revoke-self`). It has no other `secret/*`, `auth/*`, `sys/*` or
`database/creds/*` access. Its role_id + secret_id
are recorded ONCE, in one 0400 file in the `openbao-breakglass` volume, which
ONLY the `openbao-init` one-shot mounts — no app container can read it. Fetch it
once, store it offline (never in shell history or a committed file), then delete
it:

```bash
docker compose run --rm --entrypoint cat openbao-init /breakglass/breakglass.txt
docker compose run --rm --entrypoint rm openbao-init /breakglass/breakglass.txt
```

When a later release bumps the policy version, upgrade an existing install with
that pair (values go in via `-e NAME=` only — never as command arguments):

```bash
read -r -p 'role_id: ' BAO_BREAKGLASS_ROLE_ID
read -r -s -p 'secret_id: ' BAO_BREAKGLASS_SECRET_ID; echo
export BAO_BREAKGLASS_ROLE_ID BAO_BREAKGLASS_SECRET_ID
docker compose run --rm -e BAO_BREAKGLASS_ROLE_ID -e BAO_BREAKGLASS_SECRET_ID openbao-init
```

The login token lives 15 minutes, has no use-count limit, and is revoked at the end of
the run. An install that predates this feature has no break-glass role: re-init
it (dev/trial) or supply any policy-write token as `BAO_TOKEN` instead. Use of
the break-glass pair is logged once the audit device lands.

#### After upgrading from an earlier CE release

An install initialised by an earlier CE release has no embedded-worker
bootstrap token: the built-in embedded worker (`mod-worker-embedded`) is refused with 401
"Worker bootstrap token required" until that token exists. The fix is the
same upgrade run described above — `docker compose run --rm -e BAO_TOKEN openbao-init`
with an operator `BAO_TOKEN` (or the break-glass pair: `-e BAO_BREAKGLASS_ROLE_ID -e BAO_BREAKGLASS_SECRET_ID`): the run seeds the
missing token (generated inside the script, written to OpenBao only — never
shown, never in `.env`) and prints a restart hint. Then restart the two
services that read it:

```bash
docker compose restart api mod-worker
```

To confirm the seed without printing the value, grep the api log for the enrollment line (`Embedded-worker bootstrap-token enrollment seeded/updated for ...`):

```bash
docker compose logs api | grep -i "Embedded-worker bootstrap-token enrollment seeded"
```

An upgrade run with NO token cannot verify or write the slot — it only
prints an informational line; re-run with `BAO_TOKEN` or the pair as above.

#### Upgrading an install that predates the embedded worker secret

1. Take the operator `BAO_TOKEN`, or the break-glass role_id and secret_id, from
   where you stored it (your sealed offline backup; the operator token is not stored
   in OpenBao). Never paste it into chat or a ticket.
2. Read the operator token securely into the environment (keeps it out of shell
   history and process args):
   `read -r -s -p 'BAO_TOKEN: ' BAO_TOKEN; echo; export BAO_TOKEN`.
   Then run the upgrade for that one run only:
   `docker compose run --rm -e BAO_TOKEN openbao-init`. For the break-glass
   pair, use `-e BAO_BREAKGLASS_ROLE_ID -e BAO_BREAKGLASS_SECRET_ID` instead.
3. Confirm the run printed one of these lines:
   - `infrastructure/embedded-worker bootstrap_token written (generated).` The
     token was seeded on this run. Restart with `docker compose restart api mod-worker`.
   - `infrastructure/embedded-worker already present — keeping existing token.`
     The token was already there. Nothing to do.
   - `openbao-init: cannot verify the embedded-worker slot (kv get exit <N>) — not
     seeding; check the OpenBao connection and the token's read permission on
     secret/data/infrastructure/embedded-worker, then re-run.` The run could not tell
     whether the slot exists — the token it used lacks read permission on that path
     (a 403), or OpenBao was unreachable, or the call failed for another reason. It
     did NOT write a token and did NOT touch any existing one. Fix the connection or
     use a token that can read `secret/data/infrastructure/embedded-worker` (the
     operator token or the break-glass AppRole login token both can once the policy
     upgrade above has run), then re-run this step. The exit code in the message is
     diagnostic only — the run never prints what OpenBao itself reported.
4. If you skip this step, the built-in worker stays without its secret and
   keeps returning 401 "Worker bootstrap token required". A plain
   `docker compose pull && docker compose up -d` cannot write the secret. The
   run prints `infrastructure/embedded-worker: cannot be verified or seeded
   without a token on this unseal-only run`, and that line names this step.

### Required secrets (no default)

Every one of these is `${VAR:?run scripts/first-run-secrets.sh}` in the
compose file — unset means `docker compose up` refuses to start. All of them
are generated for you by `scripts/first-run-secrets.sh` into `.env`:
`POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `VERSITYGW_ROOT_ACCESS_KEY`,
`VERSITYGW_ROOT_SECRET_KEY`, `KEYCLOAK_DB_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`
(the Keycloak master-realm bootstrap admin, user `admin`),
`KEYCLOAK_REALM_ADMIN_PASSWORD` (the seeded `modtex` realm's `admin` user,
see [Keycloak realm & dev credentials](#community-edition--keycloak-realm--dev-credentials) below), `PLATFORM_SERVICE_API_KEY` (the
platform service account's API key for node scan / internal calls),
`SECRET_ENCRYPTION_KEY`, and `AUDIT_HMAC_KEY` (HMAC key used to hash each audit-log
row; Community Edition records the hashes but ships no chain verification).
The Keycloak client secrets (`KEYCLOAK_FASTAPI_CLIENT_SECRET`,
`KEYCLOAK_FASTAPI_ADMIN_SECRET`, `KEYCLOAK_DASHBOARD_CLIENT_SECRET`,
`KEYCLOAK_SERVICE_CLIENT_SECRET`) have no compose default either; they're
generated by `./keycloak/ensure-client-secrets.sh` instead (see above).

Optional (sensible non-secret defaults already applied — override only if
needed): `POSTGRES_USER` (`core`), `POSTGRES_DB` (`modcore`),
`KEYCLOAK_REALM_NAME` (`modtex`), `KEYCLOAK_SERVICE_CLIENT_ID` (`core-service`),
`KEYCLOAK_DASHBOARD_CLIENT_ID` (`dashboard-client`), `BASE_DOMAIN` (`localhost`;
`API_SUBDOMAIN` / `DASHBOARD_SUBDOMAIN` / `WORKFLOWS_SUBDOMAIN` default to
**empty**, not `localhost`),
`PROTOCOL` (`http`), `KEYCLOAK_EXTERNAL_URL` / `KEYCLOAK_HOSTNAME`,
NEXT_PUBLIC_API_URL / NEXT_PUBLIC_DASHBOARD_URL (read only by the docker-compose.dev-build.yml build args; a pulled-image install ignores them), `VGW_REGION` (`us-east-1`).

The optional vars above run fine fully offline with no env set. The required
secrets do not: `env -i docker compose -f docker-compose.yml config` now
*fails* with a `run scripts/first-run-secrets.sh` error — that's intentional
(part of the release gate) and is how a fresh checkout tells you to run the
first-run scripts before `up`.

## Community Edition — Keycloak realm & dev credentials

The overlay's `keycloak` service auto-imports `keycloak/core-realm.json` at
start (mounted at `/opt/keycloak/data/import/` + `--import-realm`, rendered
by `keycloak/render-realm.sh`). The realm is named **`modtex`** — the
frontends and API hard-code it — and it contains only the clients the CE
apps use:

| Client | Kind | Secret |
| --- | --- | --- |
| `workflow-builder-client` | public (PKCE + password grant) | — |
| `dashboard-client` | confidential | random, from `.env` |
| `fastapi-app` | confidential, service account | random, from `.env` |
| `fastapi-admin-service` | service account (Keycloak admin API) | random, from `.env` |
| `core-service` | service account (`KEYCLOAK_SERVICE_CLIENT_ID`) | random, from `.env` |

None of these secrets is a fixed value anymore: `./keycloak/ensure-client-secrets.sh`
generates a random value for each one you haven't already set, writes it to
`.env`, and both Keycloak (via `render-realm.sh`) and the apps (via compose
`${VAR}` interpolation) read the same generated value — see "Running
Community Edition" above.

One user is pre-seeded in the `modtex` realm:

- **admin@core.local**, realm role `admin`. Its password is
  `KEYCLOAK_REALM_ADMIN_PASSWORD`, generated by `scripts/first-run-secrets.sh`
  into `.env` — read it with
  `grep '^KEYCLOAK_REALM_ADMIN_PASSWORD=' .env` on the host (don't paste it
  anywhere). Keycloak may force a password change on first login because the
  realm import sets `temporary: true`; this is not yet re-proven on a clean CE
  install. If Keycloak shows an 'Update password' page, set the new password
  there; you can also change it later in the account console.
- Admin console: `http://localhost:8080`, master-realm admin user `admin`
  (`KEYCLOAK_ADMIN_USER`), password `KEYCLOAK_ADMIN_PASSWORD` (same `.env`,
  same `first-run-secrets.sh`) — the `keycloak-admin-init` one-shot service
  (`keycloak/permanentize-admin.sh`) makes that bootstrap admin permanent
  (clears the forced password-reset action) right after Keycloak is healthy,
  so the `.env` credential works as-is and `docker compose up` needs no manual
  step.

Optional: protect the admin account with MFA (opt-in — nothing is enforced until
you enroll). On the Dashboard, open **My Account** → **Security**
(`CORE/Dashboard/pages/account.html:262`) and press **Set up
2FA**; enrollment runs on the MOD-themed sign-in page (`kc_action=CONFIGURE_TOTP`),
so point any standard authenticator app (Google Authenticator, Aegis, 1Password) at the
code it shows and sign in with that code. **Replace authenticator** swaps devices;
`GET /v1/me/mfa` reports the status, and a platform admin can clear a stuck account
with **Reset 2FA** on the Users page.

⚠️ Every credential above is generated per-install into your local `.env`,
never printed by these scripts, and never committed. Still only appropriate
for a single-host/trial deployment as shipped — put real secrets management
(e.g. the bundled OpenBao, or your own) in front of anything you expose
beyond localhost.
