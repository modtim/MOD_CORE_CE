API Keys

Create and manage API keys for programmatic access to the platform

Using API Keys (OAuth 2.0 Token Exchange)

API keys are exchanged for short-lived OAuth tokens for CMMC/ISO 27001 compliance:

  1. Exchange your API key for a token: POST /api-keys/token with {"api_key": "sk_..."}
  2. Use the returned JWT in the Authorization: Bearer <token> header
  3. Tokens expire after 1 hour - request a new one when needed

Security: Your API key is never sent to other endpoints. Tokens are short-lived and fully audited.

How to use this key

Exchange the key for a short-lived bearer token (recommended), then send it as an Authorization: Bearer <token> header. The raw sk_... key also works directly on service endpoints. 

curl -X POST "$API_URL/api-keys/token" \
  -H "Content-Type: application/json" \
  -d '{"api_key":"<your sk_ key>"}'
# → { "access_token": "...", "token_type": "Bearer", "expires_in": 3600 }
# then: Authorization: Bearer <access_token>

Speed vs. safety

These three sliders decide how the system balances getting jobs done quickly against keeping your workers from getting overloaded. Pick a style for a one-click setup, or drag the sliders to dial it in. Changes are live within a few seconds — no restart.

These are the default values. Click Save to lock them in for your deployment.

Picking a style sets all three sliders below. Drag any slider to fine-tune — the style switches to Custom automatically.

30%

Background work like calibration runs only when at least this much of your worker fleet is idle. 50% means "wait until half my workers are free" — the other half stay ready for new user jobs. Higher = keep more breathing room for the people paying you; lower = let the system use idle time for itself.

70%

When workers aren't very busy, a quick "good enough" plan is fine. When they're slammed, taking a few extra seconds to pick the best arrangement saves a lot of waiting downstream. Lower = always plan carefully (a little CPU on the API, big payoff under load). Higher = save that effort for when the fleet is really packed.

15s

Some tasks are predictable ("this will take 30 seconds"). Others, the AI can only guess at. For those uncertain ones, the scheduler pads its estimate by this many seconds so it doesn't accidentally pile too many onto one worker. Higher = spread uncertain tasks across more workers (safer, but slower). Lower = trust the guess and pack them in anyway.

40%

Self-maintenance work — calibration runs and building node variants for new accelerators — shares one budget and never grows past this share of your fleet, so there's always room for real user jobs. The other slider ("keep this much free") decides when background work may start; this one caps how much it may use while running. Higher = finish self-maintenance faster (uses more of the fleet); lower = keep more of the fleet for paying work at all times.

Teach the system about your workers

Runs a batch of test workflows across every online worker. The system learns how each one performs — how long real tasks take, how much memory they use, how they share GPUs — so future predictions get sharper. Most useful right after you add new workers or roll out a new node type. Safe to leave running in the background; user jobs always take priority.

Teach the system how your nodes perform

Turn this on and the system quietly tries every node on your fleet — a few image sizes, a few inputs — just to time them. The scheduler learns “the resize node usually takes 8 seconds on this GPU” instead of guessing. The more it learns, the better it predicts how long real user jobs will take.

User work always wins. Learning only happens on idle workers, and pauses the moment user jobs need them back. (The Scheduler tab controls how much idle headroom must be free before learning steps in.)

Keep-warm containers (advanced)

                        

                            Warm containers keep a node container running between
                            calls to skip start-up time, so repeat calls to opted-in
                            nodes are faster. A warm container is never reused for
                            another tenant or another image version, its data folders
                            are wiped and
                            verified empty between calls, and each call runs as a new
                            process, so process memory cannot be shared between calls.
                            The trade-off: container memory stays held while the node
                            is idle. Both switches are off-path by default: nothing
                            runs warm until a node flags warm_policy AND a tenant
                            admin turns the tenant switch on.
                        

                    


                    

                    


                    

                        
                        
                    


                    

                        
                        
                    


                    

                


                
                

                    

                        
Per-resource leak thresholds

                        

                            Each threshold is expressed in native units per
                            credit billed. When the hourly leak scan finds
                            a (tenant, user) whose actual ratio exceeds the
                            threshold for any resource, a RESOURCE_LEAK_DETECTED
                            audit event fires for that resource. Tune lower to
                            be more sensitive on a given dimension.
                        

                    


                    

                    


                    

                        

                            
                            
                            
Default 60 — alert when a user burned more than 60 GPU-utilization-seconds per credit billed (≈ 1 minute of 100%-busy GPU per credit).

                        

                        

                            
                            
                            
Default 600 — alert above 10 minutes of single-core-busy compute per credit. Per-core, summed.

                        

                        

                            
                            
                            
Default 300 — alert when a user held 1 GB of RAM for 5 minutes per credit.

                        

                        

                            
                            
                            
Default 1000 — alert above 1 GB of cumulative IO per credit. Useful for catching dataset-exfiltration patterns.

                        

                    


                    

                        

                            
                            
                            
Default 10 — suppress alerts when a user burned fewer than this many credits in the window. Stops trivial activity from drowning the signal.
